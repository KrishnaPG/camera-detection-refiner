# Repo DX

- Every repository MUST expose one root task interface with identical targets: `bootstrap`, `doctor`, `run`, `check`, `test`, `verify`, `seed`, `migrate`, and `clean`. CI, agents, and advanced workflows MUST call these targets; CI-only/README-only workflows and hidden IDE steps are forbidden.
- Default local product startup MUST require only `docker compose up`; shutdown MUST require only `docker compose down` and no manual container cleanup. `doctor`, `seed`, `verify`, smoke runners, and setup scripts may be CI/agent/internal helpers, but MUST NOT be prerequisite human memory for first use.
- Default Compose MUST run production-shaped images. Dev-only bind mounts, HMR servers, broad toolchains, Docker socket access, and source-mounted services MUST be opt-in through an explicit dev override or host command; a fresh developer still starts the product with plain `docker compose up`. Fast dev loops SHOULD come from host-run app commands plus containerized dependencies, or explicit dev overrides, not from weakening the default production shape.
- A fresh local checkout MUST start without a hand-written `.env`. Non-secret local defaults are required; real secrets may be explicit overrides only. Missing external secrets MUST fail fast with actionable diagnostics.
- From a fresh clone, `bootstrap` MUST idempotently provision or verify pinned toolchains/dependencies and generated artifacts. Only credentials/secrets may require external input; no undocumented machine state. `doctor` MUST be read-only and verify versions, lockfile sync, typed configuration, credentials, staged services, migrations, and required paths; each failure MUST print expected state, observed state, and exact remediation.
- `check` MUST be read-only and fail fast in cost order: formatting check -> lint -> type check -> import/build -> generated/schema drift. `test` MUST obey Test Realism Rules. `verify` MUST run the exact CI path: `check` then `test`. Failures MUST return non-zero; never report partial success.
- `seed`, `migrate`, and `clean` MUST be explicit, idempotent, environment-scoped, and print the target before mutation. `clean` MUST delete only generated/run-scoped state, NEVER shared or production data.
- Runtime configuration MUST have one typed owner. Public/internal URLs, RPC endpoints, OIDC issuer/metadata/JWKS URLs, redirect URIs, CORS origins, discovery links, Traefik labels, observability endpoints, published host ports, and durable data paths MUST come from a resolved runtime profile or generated artifacts derived from it, not scattered literals.
- Docker Compose, Keycloak defaults, backend auth config, frontend runtime config, CORS policy, discovery JSON, and edge routing MUST agree with that runtime profile. Drift checks MUST compare generated config, live discovery, and browser-observed values.
- Generated runtime artifacts MUST be clearly marked generated, committed or ignored intentionally, and produced by startup guards when missing or stale. `docker compose up` MUST fail fast or self-repair before long-lived services start; developers MUST NOT remember separate generator commands.
- Backend services own generated runtime artifacts and discovery APIs. Frontends MUST ask backend/runtime discovery for URLs, auth, CORS-relevant metadata, and health/status; they MUST NOT import backend-generated files or duplicate infrastructure constants.
- Docker images MUST separate build, runtime, helper, and worker concerns. Production runtime images ship only built artifacts plus runtime dependencies: compiled Rust binaries, installed Python wheels/apps, static frontend assets, CA certs, and minimal health probes. They MUST NOT include source trees, compilers, package managers, test deps, git, Docker CLI, Snakemake/workflow tools, or `node_modules` unless that service demonstrably needs them at runtime.
- Frontend production images MUST serve built static assets from a small HTTP server; Vite/Bun dev servers are development-only. Workflow execution tooling MUST live in a dedicated runner/worker image, not in web/API or compose-helper images.
- Dockerfiles MUST maximize layer reuse: lockfiles/manifests before source, dependency install before app copy, build caches scoped to builders, and stable runtime base layers. Published images MUST avoid invalidating dependency layers for source-only changes, and upgrades MUST let registries pull unchanged layers by digest.
- Product validation MUST use a production-shaped browser origin by default: external HTTPS/WSS ingress, forwarded host/proto handling, route-level public/protected auth policy, and private service-to-service traffic over Docker/service-network HTTP, WS, or gRPC. Direct app ports and `localhost` are debug conveniences only, not acceptance targets.
- The frontend may be hosted separately from backend ingress. Local compose may publish a frontend helper, but backend/auth/RPC/admin/observability product traffic MUST enter through Traefik.
- Only Traefik publishes backend/auth/RPC/admin ingress. Private services MUST use Docker service-network HTTP, WS, or gRPC unless a separate internal-mTLS plan is approved.
- CORS MUST be configurable from day one because frontend origins may be local, CDN-hosted, cloned, or moved. Authenticated routes MUST use exact origins or controlled bootstrap rules, never wildcard `*`.
- Public backend runtime URLs MUST derive from request headers forwarded by Traefik. Network-interface IP discovery is allowed only for startup hints and smoke target selection.
- The repo MUST support both a zero-DNS dev ingress profile and a production-certificate profile. Dev ingress may use an IP-address URL plus self-signed TLS with browser warning override; production certificate mode may use ACME, Cloudflare, or platform TLS. These profiles may differ in certificate source and public addressing, but MUST keep auth, discovery, redirects, RPC, CORS, and smoke tests aligned through the same runtime-profile contract.
- Any local HTTP/IP auth exception, such as disabling browser PKCE because Web Crypto requires a secure context, MUST be explicit in the runtime profile and MUST revert to the stronger setting in certificate-backed HTTPS profiles.
- Docker ports MUST use one committed port registry. Compose/YAML files MUST reference registry-derived values for host ports, container ports, labels, commands, healthchecks, and service URLs; numeric port literals are forbidden outside the registry and tests. Registry defaults MUST be unique and grouped by class; Container-internal vendor ports may keep vendor values only as named registry entries; public host mappings MUST preserve the below class ranges:
  - `60000-60049`: edge, ingress, reverse proxies and protocol gateways
  - `60050-60199`: public applications, REST APIs, GraphQL APIs, web applications, mobile BFFs and WebSocket services
  - `60200-60399`: internal APIs, gRPC endpoints, microservices and service callbacks
  - `60400-60549`: ETL controllers, workflow engines, schedulers, message brokers, event buses, streaming systems and schema services
  - `60550-60699`: databases, caches, search systems, indexing systems and vector stores
  - `60700-60799`: object storage, distributed file storage, query engines, lakehouse services, metadata catalogs and storage gateways
  - `60800-60859`: authentication, authorization, identity, policy engines, secrets, certificates, KMS and security control-plane services
  - `60860-60899`: OpenTelemetry receivers, metrics ingestion, trace ingestion, log ingestion and observability backends
  - `60900-60939`: administration APIs, operations consoles, monitoring dashboards, database consoles and management interfaces
  - `60940-60999`: global unassigned reserve. This range MUST remain unallocated until an existing class reserve is insufficient or a new infrastructure class is formally introduced.

- Compose YAML MUST use named host variables such as `BIODOCK_LOOPBACK_HOST`, `BIODOCK_BIND_HOST`, and `BIODOCK_BIND_ALL_HOST`; raw `127.0.0.1`, `localhost`, `0.0.0.0`, and numeric port literals are forbidden in YAML outside the committed registry projection and generated `.env`.
- Compose services with persistent state MUST use stable host bind mounts under `${BIODOCK_DATA_ROOT:-~/data}/<container-name>` (or a documented service subdirectory). Named Docker volumes are allowed only for disposable/generated state; databases, caches, object stores, indexes, certificates, registries, and app state MUST survive `docker compose down` and restart. `clean` MUST NOT delete durable data without an explicit service name and confirmation gate.
- Compose validation MUST fail on duplicate published ports, out-of-range host-port defaults, unregistered port variables, persistent named volumes, missing host data mounts, and drift between the registry, `.env.example`, generated runtime profile, rendered Compose, discovery JSON, and docs/logged startup surfaces.
- Startup MUST publish required runtime knowledge through INFO logs, Docker logs, sanitized discovery/server-info JSON, and the UI Server surface. Failures MUST include stable code, failing boundary, observed/expected value when safe, sanitized target, log window, and remediation.
- Container healthchecks are readiness/liveness contracts for orchestration and startup ordering, not a substitute for product monitoring. User-visible container/service state MUST come from an explicit admin/debug status surface backed by runtime discovery, Docker/orchestrator APIs where available, logs, and app-level probes.
- Product-affecting changes to Compose, auth, routing, discovery, startup, frontend runtime config, RPC, P2FS/package flows, C-view, or observability MUST run real ingress browser smoke before completion: UI loads through HTTPS, Server info renders discovery, seeded sign-in works, workspace loads, `/rpc` connects over WSS when applicable, console/network are clean, and logs explain injected failures. Production-certificate changes MUST additionally exercise the production-certificate profile or clearly report the missing external credential/platform gate.
- Product smoke reports MUST record time to first UI, sign-in, RPC readiness, manual config count, known-command count, failure explainability, runtime-profile hash, and support artifacts: screenshot, console log, network log, discovery snapshot, Docker log excerpt, and OTel/log excerpt when enabled.
- Observability export MUST use bounded queues/batches, never block the request path, and report drops or retry exhaustion. If logs do not explain a runtime bug, improve observability before the narrow fix. Docker log scraping is local/dev convenience; supported traces may go to Langfuse, but general logs MUST use structured stdout, OTLP, or platform drains.
- Tracker status MUST distinguish `Complete` from `Implemented, awaiting product smoke`. Unit/contract tests alone cannot complete product-affecting work unless live smoke is explicitly not applicable with a reason.
- Configuration MUST have one typed schema and one committed secret-free example; startup MUST report all missing/invalid keys with expected type/source before doing work. Each tool MUST have one configuration source; do not duplicate settings across task files, CI, package scripts, editor settings, and `pyproject.toml`.
- Developer commands MUST provide `--help`, stable exit codes, and actionable errors. Every run/test MUST print its environment, run/job id, and how to locate logs/traces and run-scoped cleanup.
